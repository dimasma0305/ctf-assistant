# Reversing CTFs

Identify format, architecture, runtime, packing/obfuscation, entry points, input path, success predicate, and anti-analysis behavior. Start with strings/imports/metadata and a control-flow map, then focus on functions that transform input or reach success.

Rename entities and record semantics as they are established. Verify decompiler claims against disassembly or runtime traces when signedness, aliasing, indirect calls, exceptions, self-modification, or undefined behavior matters. Use breakpoints/watchpoints, emulation, hooks, or targeted instrumentation to expose hidden state.

Patching past a check can confirm location but does not by itself solve the player task. Extract or reproduce the actual transformation, constraint, key, or input and validate it on an unpatched binary or remote verifier.

For native binaries, begin with `python3 scripts/native_triage.py <binary>` to collect bounded metadata, mitigations, imports, symbols, sections, and string counts. Add `--match` only for a concrete hypothesis derived from the input path, success predicate, protocol, or an observed value. When code-rs is available, use `outline -l elf --format toon` for a bounded function inventory and `disasm -l elf --format toon` for one named function. Preserve its stderr truncation signal and treat an empty modeled result as uncertainty. Use interactive Rizin for targeted cross references, function graphs, or questions the smaller query cannot answer. Avoid whole-program analysis until a named function or address requires it. Save raw tool output as evidence instead of bringing it wholesale into model context. Confirm decisive decompiler or analyzer claims against instructions or runtime behavior.

When a Go metadata tool reports no `pclntab`, inspect section boundaries and table structure before accepting absence. Obfuscation may change a magic value while leaving function counts, offsets, and names recoverable. Validate candidate headers and function entries against file bounds and executable addresses, then trace only the functions relevant to the challenge. Keep this structural recovery read-only on the original sample; parse a copy or in memory.

Before paying for whole-program decompilation, test whether the decisive value or state becomes directly observable at a stable, named runtime boundary. When it does, use a targeted breakpoint, watchpoint, or dump and verify the object layout against instructions. When optimized native code or C++ abstractions still leave a targeted assembly slice too large to reason about, use an available decompiler only after a string, import, function, or address has narrowed the question. Keep one analysis session open, request direct pseudocode for the decisive functions first, and follow only references justified by observed data. Request a comprehensive function dossier only when its control-flow, p-code, or reference evidence answers a specific unresolved question. Verify the recovered transformation or value against instructions, runtime state, or the original verifier.

For a shipped Electron/JavaScript directory or ASAR, use the optional pinned REA CLI when the question depends on cross-file application structure such as HTML loads, preload exposure, or IPC pairing. Save its complete JSON to evidence, then run `python3 scripts/rea/summarize.py <result.json> --match <seed-regex>` and bring only the relevant relationship, source range, limitations, and Evidence ID into the working context. Keep `rg` and code-rs as the first choice for literal lookup, ordinary source repositories, and taint questions. Do not run REA setup or its full capability catalog during a solve; the workspace bootstrap supplies the CLI without changing agent configuration. Static relationships remain inferred until source or runtime evidence confirms reachability.

For Android APKs, prefer Droid ASC's on-demand queries over a full application decompile. Start with `droidasc getmanifest` and a package-filtered `droidasc listclass`; use `droidasc findrefs` for a concrete string, type, method, or field hypothesis; then `droidasc getclass` only for the classes that can reach the input or success predicate. Save large results to evidence files and bring only the decisive excerpts into context. Verify ambiguous decompiler output against DEX instructions or runtime behavior.
