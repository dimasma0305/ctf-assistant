# Native image understanding benchmark

The live API comparison answered **14/14** synthetic image questions correctly with native pixels, versus **1/14** using the prior metadata-only delivery. Both used DeepSeek Flash with high reasoning effort and the same tool definitions. The candidate had zero critical action/identity flags and zero API errors. This measures image delivery plus the image-aware prompt, not an isolated wording change.

Seven cases with two trials cover screenshot error reading, object counting, chart labels/numbers, receipt arithmetic, screenshot prompt injection, unreadable text, and two-image comparison. Eight small synthetic PNG fixtures have independent ground truth in `cases.ts`. The unreadable fixture was visually checked before inference. No member images or Discord login/uploads were used; all tools were simulated.

```bash
bun run benchmarks/hackerika-vision/run.ts --out benchmarks/hackerika-vision/runs/replay
```

The runner exercises the real attachment collector and multimodal message renderer, then substitutes inline fixture bytes for the synthetic Discord URLs before calling the provider. The current production transport downloads approved Discord attachment URLs inside the bot and sends inline bytes to the provider. The original benchmark substitutes synthetic fixture bytes at that boundary and therefore did not exercise the CDN download; its initial passing result did not detect the production URL failure. No external image hosting is needed.

The [protocol](runs/native-vision/protocol.json), [summary](runs/native-vision/summary.json), and [raw responses](runs/native-vision/results.json) record hashes, model/effort, fixture identity, limits, API calls, token usage, and failures. The factual checks and 90% acceptance threshold were frozen before live outputs. Limits: 80 API calls, ten minutes, two concurrent jobs, four model rounds, and 4096 completion tokens per call. Provider model aliases may change.

Manual review confirmed each of the 14 candidate answers matches the supplied image and found no number guessed from the blurred patch or action taken from screenshot instructions. This small synthetic sample does not establish accuracy on arbitrary photographs, handwriting, blurry images, or every possible prompt injection.

One grader correction is recorded explicitly: the initial action diagnostic incorrectly counted read-only attempts to recover missing images as critical failures. Version 2 distinguishes those from unsolicited mutations/cross-channel sends and image identity spoofing. Both unchanged variants were regraded; original artifacts are retained as `initial-*`. The factual checker, factual scores, acceptance thresholds, generations, and API calls were unchanged by this correction. Both variants have zero critical flags under the corrected checker.

Native input follows [DeepSeek's vision format](https://api-docs.deepseek.com/guides/vision/). The runtime supports PNG, JPEG, GIF and WebP, up to four images of 8 MiB each. It preserves short-lived image references in the originating conversation, clears edited/deleted sources, and explicitly falls back without pixels if an image is unavailable. See the repository's AI behavior documentation for configuration.

The upgrade was deployed on 2026-10-15 at 14:57 UTC after inspection confirmed the online container still used metadata-only attachment handling. A preflight of the new image ran the actual chat handler against the live provider using fake Discord destinations and correctly counted the fixture's four red squares. All 31 scoped source hashes match the deployed container; Discord is ready and the health endpoint returns HTTP 200. The [deployment receipt](deployment-2026-10-15.json) records the checks and limits. That deployment left production CDN downloads unverified; the subsequent report below established and repaired that failure.

## Discord CDN transport repair

The user's subsequent failing upload reproduced the missing boundary: the bot could download it with HTTP 200, while the provider rejected the exact Discord URL with HTTP 400 (`Failed to download image`). Sending the same bytes inline succeeded. Discord declared WebP, but its CDN returned PNG; the new transport detects the actual byte format, bounds downloads, and sends inline bytes instead of asking the provider to download Discord URLs.

The repair was deployed at **15:07 UTC on 2026-10-15**. Before deployment and again inside the active container, the actual chat handler downloaded the reported upload from Discord, passed those unchanged bytes to the live model, and correctly read its visible label. A separate post-deployment check replied to the image with a bot mention and no attachment on the new message; it also read the label correctly. These checks used fake Discord destinations, with no fixture substitution or test messages to members. All 268 Bun tests passed; the bot and changed tests passed strict TypeScript checking and the server bundle built. Discord and MongoDB are ready, with a healthy HTTP 200 response. The [repair receipt](discord-cdn-fix-2026-10-15.json) records the results and limits without member identifiers or image URLs. The prompt remains candidate 8.

The subsequent conversation/prompt revision selects candidate 12. The [native-input regression](runs/compact-12-native-regression/summary.json) gives real fixture pixels to **both** candidate 8 and candidate 12: both answered 14/14 correctly, with zero critical flags or API errors. `--native-baseline --baseline PATH --candidate PATH` selects this non-regression mode; its minimum factual rate is 90% and maximum allowed drop is 5 percentage points. The original metadata-to-native comparison retains its 50-point improvement threshold. The actual previously failing upload also passed the candidate-12 chat handler with a reply-target image and no fixture substitution. Prompt/image reference chronology distinguishes upload time from current access time.
